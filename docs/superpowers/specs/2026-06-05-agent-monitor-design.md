# AgentMonitor Full Product Blueprint

Date: 2026-06-05
Status: Approved design for written review

## 1. Product Goal

AgentMonitor is an open-source passive observability system for agent task execution. It monitors multiple agent sessions across multiple machines and agent products, records structured lifecycle events, infers task status, and presents a compact desktop dashboard with an optional floating status window.

The system does not control agents. It does not pause, resume, modify, or steer agent execution. It only receives events, stores metadata, derives status, and displays current and historical activity.

The intended deployment model is the same for local and cloud usage. A local single-user deployment can run without a token and use the `default` user. A cloud or multi-device deployment can use tokens to separate users. Switching between local and cloud should only require changing the server URL and optional token.

## 2. Design Principles

- Protocol first: server and frontend understand a generic Agent Monitor Protocol, not Codex-specific internals.
- Passive monitoring only: no server-to-agent command channel.
- Lightweight by default: SQLite works locally without extra services; Postgres is a first-class backend for cloud or heavier usage.
- Metadata over logs: store state, metadata, and explicit hook/agent event records, but not full agent logs.
- Adapter-based integration: Codex, Claude Code, other agents, CLI wrappers, hooks, skills, and MCP tools all emit the same event model.
- Extensible events: standard event types cover common behavior, while adapters can add namespaced events.
- Dashboard first: the frontend is a practical live monitoring surface, not a marketing site or complex admin panel.

## 3. Non-Goals

- No remote control of agents.
- No complete prompt, assistant response, terminal stdout, or environment capture by default.
- No OAuth, organizations, teams, or complex role-based access control.
- No dependency on one agent product's private data model.
- No separate local-only architecture that diverges from cloud deployment.

## 4. Top-Level Task Model

The top-level monitored unit is an agent session or thread.

A session represents one continuous task execution context, such as one Codex thread, one Claude Code session, or one wrapped agent process. Sub-events under the session record messages, tool calls, command execution, permission waits, heartbeats, errors, and lifecycle completion.

Each session has:

- session id
- owner user id, derived from token or `default`
- agent type, such as `codex`, `claude_code`, or `generic`
- adapter name and adapter version
- agent-written summary when available
- fallback title derived from metadata when no summary is provided
- machine metadata
- workspace metadata
- repository metadata
- started time
- last event time
- last heartbeat time
- inferred current status
- terminal lifecycle result, if finished

## 5. High-Level Architecture

```text
Codex hook / skill / MCP tool
Claude Code hook / skill / MCP tool
Other agent wrapper / CLI
        |
        v
Agent Monitor Protocol
        |
        +--> HTTPS Ingest API  <--- MCP Gateway
                 |
                 v
           Event Store
       SQLite default / Postgres optional
                 |
                 v
        Query API + Status Engine
                 |
                 v
      Tauri Dashboard + Floating HUD
```

The canonical write path is the HTTPS ingest API. MCP is an adapter and gateway that exposes agent-friendly tools, then writes into the same ingest path and event store. This keeps hooks, CLI wrappers, agents with MCP support, and agents without MCP support compatible with one system.

## 6. Agent Monitor Protocol

The Agent Monitor Protocol defines the event schema. It is independent from transport. The same event can arrive through HTTPS, MCP, a hook adapter, a skill, or a CLI wrapper.

### 6.1 Event Envelope

Each event is append-only and should include:

- `event_id`: globally unique event id generated by client or server
- `session_id`: stable id for the monitored agent session
- `user_id`: owner resolved from token, or `default`
- `agent_type`: product family, such as `codex`
- `adapter_name`: emitting integration, such as `codex-hook`
- `adapter_version`: integration version
- `event_type`: standard or adapter-specific event type
- `event_time`: time observed by the client
- `received_time`: time accepted by the server
- `sequence`: optional monotonic sequence for ordering within a session
- `severity`: `debug`, `info`, `warning`, or `error`
- `summary`: optional short human-readable event summary
- `machine`: hostname, OS, architecture, user, and stable machine id if available
- `workspace`: cwd, repo root, git branch, git commit, and project name if available
- `payload`: structured metadata specific to the event
- `dedupe_key`: optional key for idempotent retries

### 6.2 Standard Event Types

Standard event types:

- `session.started`
- `session.heartbeat`
- `session.summary.updated`
- `message.started`
- `message.finished`
- `tool.started`
- `tool.finished`
- `command.started`
- `command.finished`
- `permission.requested`
- `permission.resolved`
- `user_input.waiting`
- `external.waiting`
- `session.completed`
- `session.failed`
- `session.aborted`

Adapters may add namespaced event types without server changes, for example:

- `codex.goal.updated`
- `codex.plan.updated`
- `codex.compaction.started`
- `claude.todo.updated`
- `adapter.offline_queue.flushed`

### 6.3 Summary Rules

Session summaries use this priority:

1. Use the agent-written summary if the agent or MCP/skill integration provides one.
2. If no summary is provided, derive a fallback from metadata such as cwd, repo, branch, first user request summary if available, or launch command.
3. Mark fallback summaries as inferred so the dashboard can distinguish them from agent-written summaries.

### 6.4 Privacy Rules

The default payload must not store:

- full user prompt
- full assistant response
- complete terminal stdout or stderr
- API keys
- full environment variables
- secrets from `.env` files or shell configuration

Allowed default metadata includes:

- event type
- tool name
- command executable and short command label
- pid
- exit code
- duration
- error class
- short error summary
- file path or cwd when useful
- token/model counters if provided by the adapter
- heartbeat interval and freshness

A later explicit debug extension can add content capture with redaction. That extension is not part of the default protocol behavior.

## 7. Status Inference

The server derives current status from events instead of requiring one fixed status field from clients.

Status is based on:

- most recent lifecycle event
- most recent heartbeat freshness
- active `*.started` events without matching `*.finished`
- explicit waiting events
- terminal events such as completed, failed, or aborted
- event severity and error summaries

Recommended derived statuses:

- `starting`: session exists but has not produced a normal heartbeat or work event
- `running`: recent heartbeat or active work event
- `tool_running`: latest active unit is a tool
- `command_running`: latest active unit is a command
- `waiting_user`: latest significant event asks for user input
- `waiting_external`: latest significant event waits for an external dependency
- `stale`: heartbeat is older than the configured freshness threshold
- `completed`: session emitted `session.completed`
- `failed`: session emitted `session.failed` or terminal error
- `aborted`: session emitted `session.aborted`

The dashboard should also show the latest raw event type because status detail should be at least as expressive as hook coverage.

## 8. Server Design

The server is a lightweight FastAPI service.

Core modules:

- ingest API: accepts events, validates schema, resolves token owner, writes to event store
- session service: maintains session rows and denormalized current state
- status engine: derives status from the latest session event graph and heartbeat freshness
- query API: serves live sessions, historical sessions, and event timelines
- MCP gateway: exposes MCP tools that record the same events
- retention job: cleans historical data according to configuration

### 8.1 Storage

SQLite is the default local backend. It should work with a single server process and no extra service dependency.

Postgres is a first-class backend for cloud or heavier usage. The schema should be relational and migration-driven so both backends share the same conceptual model.

Main tables:

- `users`
- `tokens`
- `sessions`
- `events`
- `session_status_snapshots`
- `machines`
- `retention_runs`

Events are append-only. Session rows may be updated with denormalized status for fast dashboard queries.

### 8.2 Authentication

Authentication is token-based only.

- If a request includes a known token, events belong to that token's user.
- If no token is provided, events belong to the `default` user.
- Unknown tokens are rejected.
- No OAuth, team model, organization model, or RBAC is included.

### 8.3 HTTP API

Canonical endpoints:

```text
POST /api/events
GET  /api/sessions/live
GET  /api/sessions
GET  /api/sessions/{session_id}
GET  /api/sessions/{session_id}/events
GET  /api/users/current
GET  /api/health
```

The ingest endpoint accepts both single events and small event batches for offline queue flushes.

### 8.4 MCP Gateway

MCP tools:

```text
agent_monitor_start_session
agent_monitor_record_event
agent_monitor_heartbeat
agent_monitor_finish_session
agent_monitor_get_session_status
```

`agent_monitor_get_session_status` is read-only. It exists so an agent can inspect what the monitor has recorded, but it must not return control instructions.

## 9. Adapter Design

Adapters produce protocol events. They should be small, transparent, and replaceable.

### 9.1 Codex Adapter

Codex integration should support:

- hook-based reporting when Codex exposes useful lifecycle hooks
- MCP or skill-based reporting when hook coverage is incomplete
- automatic metadata capture for cwd, hostname, repo, branch, session or thread id, and launch context
- agent-written session summary when available
- heartbeat while a session is active
- terminal lifecycle event on completion, failure, or abort

Codex-specific event extensions may use the `codex.*` namespace.

### 9.2 Claude Code Adapter

Claude Code integration follows the same event mapping:

- hook events when available
- skill or MCP events when hooks are missing
- command/tool/wait/finish event mapping into the standard event set

Claude-specific extensions may use the `claude.*` namespace.

### 9.3 Generic CLI and Wrapper

A generic CLI supports agents, scripts, and long-running commands without native integration.

Expected commands:

```text
agent-monitor run --agent codex -- <command>
agent-monitor event ...
agent-monitor heartbeat ...
agent-monitor finish ...
```

The wrapper records command metadata, pid, exit code, duration, and short error summaries. It must not persist complete stdout or stderr by default.

### 9.4 Reliability

Adapters should support:

- server URL configuration
- optional token
- session id generation or explicit session id input
- configurable heartbeat interval
- short retry on transient ingest failure
- local bounded queue for offline events
- payload redaction before sending

The queue should be bounded so a broken server cannot fill local disk.

## 10. Tauri Dashboard

The desktop frontend is built with Tauri and React/TypeScript. It is a compact operational dashboard with a floating HUD.

### 10.1 Main Dashboard

The default view is a live sessions table. Each row shows:

- status indicator
- agent type
- adapter
- agent-written or inferred summary
- machine
- workspace path
- repo and branch
- latest event type
- last heartbeat age
- duration
- started time

Clicking a session opens detail view with:

- session metadata
- inferred current status
- event timeline
- key lifecycle events
- heartbeat history
- error summaries
- adapter payload metadata

The dashboard should support recent history search by user, agent type, machine, path, status, and time range.

### 10.2 Floating HUD

The floating HUD is an always-on-top compact status window.

It displays:

- running count
- stale count
- failed count
- waiting user count
- latest important event
- last update age

It supports:

- global hotkey to show/hide
- compact mode
- transparent or minimal chrome mode
- status color changes
- position and opacity controls
- quick open into the full dashboard

### 10.3 Notifications

Notifications are local to the Tauri app.

Triggers:

- session becomes stale
- session fails
- session completes
- session waits for user input
- heartbeat resumes after stale

Notifications are not a control channel. They only surface server-derived status changes to the local user.

### 10.4 Visual Direction

The UI should be quiet, dense, and scan-friendly. It should look like a practical engineering dashboard, not a landing page. It should avoid decorative hero sections and focus on fast recognition of which agents are running, stale, waiting, failed, or completed.

## 11. Deployment and Configuration

Local and cloud deployment use the same server.

Important configuration:

- server bind host and port
- database URL
- token map
- default user behavior
- heartbeat freshness threshold
- event retention days
- session retention days
- allowed CORS origins for dashboard
- adapter redaction rules

Example local shape:

```text
AGENT_MONITOR_SERVER_URL=http://127.0.0.1:8766
AGENT_MONITOR_TOKEN=
AGENT_MONITOR_DATABASE_URL=sqlite:///agent_monitor.db
```

Example cloud shape:

```text
AGENT_MONITOR_SERVER_URL=https://monitor.example.com
AGENT_MONITOR_TOKEN=<user-token>
AGENT_MONITOR_DATABASE_URL=postgresql+psycopg://...
```

## 12. Security and Data Handling

Security requirements:

- token values are never displayed in event timelines
- secret-like payload keys are redacted before storage
- adapters should redact obvious env and API key names before sending
- server should reject oversized payloads
- server should keep request logs from storing full event payloads when possible
- dashboard should not expose sessions across token-derived users

Because the product is open-source and self-hostable, simple configuration must be enough for local use. Cloud users can harden deployment with TLS, reverse proxy auth, backups, and Postgres.

## 13. Testing and Acceptance Criteria

Protocol and server acceptance:

- event ingest accepts valid standard events
- invalid event shapes fail with clear validation errors
- no-token ingest assigns events to `default`
- known-token ingest assigns events to the configured user
- unknown tokens are rejected
- session status updates from heartbeat, waiting, failure, completion, and stale timeout
- event timelines preserve append-only order
- SQLite and Postgres backends share the same behavior

Adapter acceptance:

- Codex adapter can start a session, send heartbeat, record tool/command events, and finish
- MCP tools write the same event records as HTTP ingest
- CLI wrapper records command lifecycle metadata without storing full stdout
- offline queue flush deduplicates events by `dedupe_key`
- redaction removes configured secret fields

Dashboard acceptance:

- live sessions table shows current sessions and updates without reload
- session detail shows event timeline and metadata
- floating HUD shows aggregate counts
- global hotkey shows and hides the HUD
- local notifications fire for stale, failed, completed, and waiting-user transitions
- dashboard works against local SQLite-backed server and remote Postgres-backed server

## 14. Open Extension Points

The blueprint intentionally leaves these as extension points, not required defaults:

- richer content capture with explicit opt-in and redaction
- metrics export to Prometheus
- multi-dashboard sharing
- hosted cloud service packaging
- richer agent-specific timelines
- per-project dashboards
- alert routing to Slack, Feishu, or email

These extensions must preserve the passive monitoring boundary unless the product direction is explicitly changed.

## 15. Final Design Decision

AgentMonitor will use a protocol-first architecture with HTTPS as the canonical ingest path and MCP as a first-class gateway. It will store event metadata and inferred session state, not complete agent logs. It will support the same open-source server for local and cloud deployments, default to SQLite locally, support Postgres for cloud, and present a Tauri dashboard with a live sessions table plus floating HUD.
